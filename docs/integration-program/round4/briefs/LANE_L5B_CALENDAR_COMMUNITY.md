Worktree `wt-r4-calendar2`, branch `wt/r4-calendar-community`, migration `0088`. Dispatch after L5a (`wt/r4-calendar`, `0085`) has landed. Code refs are at game-amora `135db66`; line numbers are hints, anchor by content. Everything L5a is expected to leave (`server/lib/calendar.ts` with `listCalendarItems`, `events.kind`/`layer`, `event_rsvps.occurrence_key`, `client/src/components/calendar/*`) is a hypothesis until you measure it on the main you cut from.

## Objective

Give the calendar its community half: a capped waitlist that promotes only into a free seat, structured slots an event declares (dish, ride, childcare, setup crew), "meet me" windows as a calendar kind, the UI for the layers L5a put in the table, a who-is-here band from stays, print for wheel and month, and the weekly brief: a zero-token template digest, in-app and by email, in village time on an admin-chosen evening, opt-out per member, never touching the interactive assistant budget.

## Why

Proposal §5 items 8-11; §8 item 26 (the L5a/L5b split) and 27 (occurrence identity, which the waitlist reuses); §9.2 A4 (weekly brief, Sunday evening, opt-out) and A5 ("meet me" windows as where introductions land); §4 item 3 (one rationed brief, zero tokens, R25 posture); §9.3 C4 (v1 layers: mine, admin, village, public). Rulings: R28 ("yes if not mentioned"), R29 (one calendar per village; A1-A7 and C1-C4 stand), R30 (go signal; N1-N8 at defaults). Measured at `135db66`: `rsvp()` in `server/lib/gatherings.ts` locks the events row `FOR UPDATE` and refuses `full`, the only capacity truth; `withdrawRsvp` is a bare DELETE with no lock; no waitlist, slot or layer table exists; `stays` has `arrive_on` and `status` and no departure date; `quests` has no `created_at`; no test hits `/api/events`; the scheduler is interval-only, so "an evening in village time" is an hourly job that acts once the local day and hour arrive (the `stay-nightly` idiom).

## Design

1. **Waitlist (§5 item 8).** `0088`: `event_waitlist` (id, event_id, user_id, occurrence_key `varchar(10) NOT NULL DEFAULT ''` mirroring `event_rsvps`, created_at(3), promoted_at, left_at; unique `(event_id, user_id, occurrence_key)`, NOT NULL because MySQL unique indexes exempt NULLs). `POST /api/events/:id/waitlist` (auth, `event.rsvp`, `events.rsvp_enabled`) joins only when `rsvp()` would answer `full`; `DELETE` leaves. `promoteWaitlist(conn, eventId, occurrenceKey)` runs INSIDE the transaction that freed the seat, after the `FOR UPDATE` on the events row that `rsvp()` already takes: on going to maybe/declined, on withdraw (move it into a transaction with that lock), and on `updateGathering` raising capacity. It promotes the oldest un-promoted rows one at a time while `going < capacity`, writing a `going` RSVP with idempotency key `waitlist:<eventId>:<userId>:<occ>`, stamping `promoted_at`, then a notification (`type waitlist_promoted`, same dedupe). No priority for anyone. `Gathering` gains optional `waitlistCount`, `myWaitlistPosition`.
2. **Slots.** `event_slots` (id, event_id, kind `varchar(24)` from `SLOT_KINDS = dish|ride|childcare|setup|other`, label, needed default 1, note, sort_order, is_example) and `event_slot_signups` (id, slot_id, user_id, occurrence_key, note, created_at; unique `(slot_id, user_id, occurrence_key)`). Crew (`event.manage`) declares slots in `EventsAdminPanel`; `POST/DELETE /api/events/:id/slots/:slotId/signup` under `FOR UPDATE` on the slot row refuses past `needed`. `GET /api/events/:id/slots` returns counts to anyone who may see the event and names only to a viewer whose own RSVP is `going` or who holds `event.manage`. Never emails.
3. **Meet-me (A5).** `kind = 'meet-me'` (in L5a's enum per its brief; if absent, `0088` appends it, enums are ordinal). `POST /api/events/meet-me`: any signed-in member with `event.rsvp` creates a window on layer `village` or `private` (title templated "Meet <first name>", start, end, place, one-line note; `created_by` = member), capped at 7 open windows per member and one per hour via `overLimit`; owner cancels. L7 reads them through `listCalendarItems({kinds:["meet-me"]})`.
4. **Layers UI (§5 item 9, C4).** v1 surfaces: `private` ("mine"), `village`, `public`, `admin` read-only marks; `circle` and `household` stay in the enum with no UI. A member's request for `public` saves as `status draft`, `layer public`, shown to its creator as "waiting for the crew" and to the crew in `EventsAdminPanel` as "Approve for the public calendar", where the existing `PUT /api/admin/events/:id` flips status. `WeekView`/`MonthView` gain layer chips (filter, localStorage) and a pill per item. Every read goes through `listCalendarItems`, which applies layer visibility server-side; the client never filters for privacy.
5. **Who is here (§5 item 11).** `GET /api/events/who-is-here?from=&to=` above `/api/events/:id` (the `by-structure` pattern), 404 when `effectiveLifecycle("stays") === "off"`. Arrivals = `stays.arrive_on` in window with status `requested|active`; here now = `active`; departures only from a real date (none at `135db66`, and `wt-housing`'s `0077` adds none): "left" from `status = ended` and `updated_at`, never an invented date. Names when the viewer is admin or holds `map.viewPeople` (`GET /api/map`: "anonymous visitors get STRUCTURE only"), counts otherwise with no `user_id` or name key present. `WeekView` draws it as a band above the days.
6. **Print.** `PrintButton` on `YearWheel` and `MonthView` (`window.print()`) plus one `@media print` sheet `client/src/components/calendar/print.css`: hide nav and controls, light background, grid and wheel to page width, zone name and both month names in the header. No images.
7. **The brief.** `calendarBrief.ts` gathers, for a week window in `SeasonConfig.timezone`, from `listCalendarItems` and item 5: arrivals and departures (per tier), meals and gatherings (`kind gathering`, layers that recipient may see), moon and season marks (`kind sky|season|cycle-mark`, written by L5a; no astronomy here), open seats (`listOrgRoles` + `listOrgAssignments`, count plus up to five role names), new quests (`quests.created_at` in the window; `0088` adds it `timestamp NULL DEFAULT CURRENT_TIMESTAMP`, existing rows stay NULL and are never called new; if the coordinator declines the column, "open quests" capped at five), and `opportunities: string[]` (empty until L7; an empty section is omitted, never filler). `renderWeeklyBrief(input)` in `assistantTemplates.ts` returns `{subject, text, html}` under that file's rule: never throws, drops a section whose data is not the shape it expects rather than guessing; strings pass `check-voice` (`SCAN_ROOTS` includes `server`). No model, no key, no `assistant_usage` row, no `assistant-day:` bucket: never import `assistant.ts`, never call `assistantDailyCapReached`/`AtLimit` (the note above `assistantDailyCapAtLimit` says why a timer must not spend the interactive budget; `synthesisBatch.test.ts` "a timer has no actor" is the K2 pattern).
8. **Delivery.** `runWeeklyBrief(deps, {weekKey, timezone})` in `notify.ts`: `resolveNotifyPrefs` gains `weeklyBrief: "on"|"off"` (default on); `emailCadenceFor("weekly_brief")` returns `"off"` on purpose so `insertNotification`'s immediate path never emails a flattened body; the sender inserts the in-app row (title "Your week at <project>", one-line body, link `/events?brief=<weekKey>`, dedupe `brief:<weekKey>:<userId>`) and, only when fresh, opted in, `emailsOff` false and `underDailyCap`, sends its own HTML and stamps `emailed_at`. A second run in the same week sends nothing. `/events?brief=` opens a `WeeklyBrief` panel over `GET /api/events/brief?week=` (auth) with the opt-out toggle (`PUT /api/profile/prefs {notify:{weeklyBrief:"off"}}`; the route already merges notify keys). The email footer says where to turn it off.
9. **Schedule.** `registerJob("weekly-brief", 60*60*1000, ...)`: read `moduleConfig("events")?.brief ?? {enabled:true, day:0, hour:18}` inside the closure, local weekday and hour via `Intl.DateTimeFormat` in `SeasonConfig.timezone` (the `todayInTz` idiom), act only when both have arrived and `effectiveLifecycle("events") !== "off"`; `weekKey` = that evening's local date. `EventsAdminPanel` gets a "Weekly brief" card (on/off, day, hour, "preview for me" that sends nothing).
