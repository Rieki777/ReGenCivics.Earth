## Ranked findings

### HIGH · QA2-01 · One member moved 130 into the gratitude ledger in a cycle capped at 100 and 30

LOCAL. `POST /api/gratitude` then `POST /api/game/gratitude/send`. No viewport (API).

The two live gratitude routes write different values into the same `cycle_id` column. The
acknowledgement route writes `lunar-000329`; the Hearts route writes `moon-329`. The acknowledgement
route's budget check reads `gratitude_log` filtered on `cycle_id = ?`, so it sees only its own half.

Measured, in one lunar cycle, with one member:

```
spend the Hearts allowance:       30 accepted, then "You can still give 0 this moon"
GET /api/game/gratitude/me:       {"total":100,"spent":0,"remaining":100,"cycleId":"lunar-000329"}
spend the acknowledgement budget: 100 accepted
gratitude_log by cycle_id:        lunar-000329 = 100, moon-329 = 30      TOTAL 130
```

The coordinator's addendum names the overlap itself as an open product decision and not a defect.
This is the other thing it named: the sum exceeds both caps. The `/api/gratitude` header in
`server/index.ts` states that "this route's allowance already counts what the older one spent, which
makes this the stricter of the two and never the looser." That is true in one direction and not in
the other, and it is the direction the header does not mention that lets 130 through.

Repro: register a member, drain `/api/gratitude` (amount 1, a fresh `clientNonce` each time) until
it refuses, read `/api/game/gratitude/me`, then send `gratitude.base_budget / 4` to each of four
recipients through `/api/game/gratitude/send`. Probe:
`scripts/qa/r6-adversary/inv1d-cycle-id-split.mjs`.

> "I gave away thirty, the page told me I had given away nothing, and it let me give away a hundred more."

### HIGH · QA2-02 · Every Hearts gift is invisible to the moon settlement

LOCAL. The same split, seen from the other end.

`settleCycle` filters on the row's own `cycleId` matching the cycle being settled, which is always
`lunar-NNNNNN`, and `parseCycleId` accepts only that shape and returns null for `moon-329`. Run the
product's own settlement functions over the product's own rows:

```
gratitude_log by cycle_id:             {"lunar-000329":101,"moon-329":39}
settleCycle(entries, "lunar-000329"):  5 recipients, 101 received
total actually in the table:           140
rows the settlement did not see:       39
dueCycles(40 days on):                 ["lunar-000329"]   (moon-329 is not a candidate)
```

Every settlement row reads `receivedHearts: 0`. That is the fallback-is-a-claim shape: the field is
a fact-shaped number that can never be anything but zero, so a recipient who was thanked nine times
is told they were thanked zero times, and their share of the pool is computed from the same number.
A cycle whose only activity came through `/api/gratitude` is never even listed as due for closing.

Probe: `scripts/qa/r6-adversary/inv1e-settlement-blind.mjs`.

> "Nine people thanked me this moon and the moon's own ledger says nobody did."

### HIGH · QA2-03 · A lone admin mints tokens to their own account, in any amount, per token

LOCAL. `POST /api/admin/tokens/:slug/mint`.

The coordinator's addendum asked me to treat "co-signed manual grants, specified in the build doc,
not built" as a hypothesis. **The hypothesis is correct.** The route has real guards: admin only,
the token must exist and be platform-governed and not an example, a positive amount, a required
written reason, and an aggregate per-cycle ceiling `ledger.admin_mint_cycle_cap` enforced both
pre-flight and inside the transaction. It has no second-steward requirement at any amount, and it
never compares `toUserId` with the acting admin.

```
self-grant of 25 to the caller's own id -> 200, their gratitude ledger 20 -> 45
single grant of 101                     -> 200, credited in full  (the doc's threshold is 100)
credits / library-credit / stay-credit / village-voice, 500 each, all to self -> 200 x 4
```

The cap is per token per cycle, so the reachable total is 10000 multiplied by the number of
platform-governed tokens, per lunation, self-directed, unwitnessed by anybody but the admin audit
trail.

The sharp edge is `village-voice`. In `governance.weight_mode = token` that token's balance IS
voting weight, so an admin can mint themselves the electorate. The freeze (invariant 2) means they
cannot do it to a ballot already open; nothing stops them doing it the minute before one opens.

Ordinary members are refused this route: 401, checked in the same run.

Probe: `scripts/qa/r6-adversary/inv1f-manual-grants.mjs`.

> "The person who runs the software paid themselves and nobody had to agree."

### HIGH · QA2-04 · A warning badge takes a member off every voting roll, and the product tells them the wrong reason

LOCAL. `POST /api/admin/badges` then `POST /api/admin/badges/:id/award`.

`buildElectorate` is honest about this in its own header ("a warning badge's deny suspends voting"),
so the mechanism is deliberate. What it produces is not.

```
POST /api/admin/badges {kind:"warning", denies:["ballot.vote"]}   -> 200
award to a member                                                 -> 200
ballot opened afterwards: electorateCount 4, she is absent from ballot_electorate
her vote -> 409 "You are outside this ballot's electorate. Who may vote froze when it opened"
GET /api/badges/of/<her id> -> {"badges":[]}
```

Four things stack here.

1. One admin removes any member from every future ballot with one award. `ballot.vote` is
   deliberately non-transferable (house rules section 7 item 2), so there is no ceremony by which the
   village could ever take this power back. The deny side is a hole in the exact wall the
   non-transferability is protecting.
2. The badge is **invisible on her own badge surface.** Control in the same run: a plain granted
   badge awarded to the same member on the same request renders on `GET /api/badges/of/<id>`; the
   warning badge does not. She holds two badges and the surface shows one.
3. She is notified once, at award time ("A warning was placed: ..."), and nothing anywhere connects
   that notice to the vote she can no longer cast.
4. **The sentence she reads is false.** "Who may vote froze when it opened" names the freeze. She was
   a member before it opened. The real reason is the badge, and the product never says so.

The deny itself is otherwise sound: 4 evasions refused, and it correctly stops an admin breaking the
glass. The badge route also accepted a warning denying `forum.post` and one denying `member.vouch`
while refusing two keys it does not know; I did not test whether those two bite.

Probe: `scripts/qa/r6-adversary/inv6-deny.mjs`.

> "I was taken off the voting roll by one person, the reason is on no page I can see, and the product told me it was because I was late."

### MED · QA2-05 · A revoked session token still writes usage marks

LOCAL. Any public-tier module route.

`meterUserId` reads the token signature and returns the user id without the `tokenVersion` check
that `authedUser` applies, so a signed-out or revoked session keeps metering.

```
member's first GET /api/library        -> 1 mark   (control)
POST /api/auth/logout                  -> 200
GET /api/profile with the same token   -> 401      (the session really is dead)
GET /api/badges with the same token    -> 200, and badges marks 0 -> 1
```

Bounded: it cannot inflate past one mark per member per module per cycle, so this is not a way to
manufacture reach. What it does is put people the village has signed out, or removed, into
`membersReached` and into the `activeMembers` denominator for the rest of the lunation, in a number
that is reported upstream to the pool.

Probe: `scripts/qa/r6-adversary/inv1b-meter-retest.mjs`.

## Refusals and corrections

**1. House rules section 7 item 4 is out of date on this build, in the product's favour.** It says
`mayAct` writes the public "acted on a power" line before the route runs, so a break-glass followed
by a validation failure leaves a record of an act that did not complete. On `b5bed01` I drove that
exact sequence on `feed.announce` and got the opposite: the override plus a body the route refuses
(400) wrote **zero** public rows, while the same override with a valid body wrote **exactly one**.
The attempt goes to the admin trail as an override line and the failure as an override-incomplete
line; the village is told about neither. I tested one key end to end and read the rest: all 49
capability-gated route sites go through `mayAct` and its response seal, and `recordAdminReach` has
no other caller. Worth a fix lane confirming the remaining keys rather than trusting my one.

**2. My own first sweep of the dormant-column instruction was wrong and the control caught it.** A
heredoc collapsed a double-escaped word boundary to a literal backspace character, so half the
matcher never ran and `quorum_pct` came back as read by nothing. The fixed run reports 0 dormant of
55 policy columns with all four controls landing. I am reporting the broken run because "a control
that did not run is not a control" is the rule that saved this one.

**3. Three of my own invariant-5 hits were mine, not the product's.** "Founder" in `/api/roles` is
the role name Founders Circle with an empty holders list; "Founder" in `/api/content/roles` is the
word inside a role's domain text; `kind: "village"` in `/.well-known/village.json` is the protocol
kind, not a holder's kind.

**4. `/api/work-with-us/attachment` answering 200 to an anonymous multipart POST is not a finding.**
It is the public applications form and it is meant to be open. I checked what it stores rather than
what it answers: the geotagged fixture goes in at 6857 bytes carrying a camera tracer and a GPS
block, and lands on the volume at 6682 bytes carrying neither. An HTML file to the same door is
refused with "Only images or PDF are allowed".

**5. `/api/notifications?userId=<somebody else>` answering 200 is not a finding.** It returns the
caller's own 31 rows, byte-identical to the same call with no parameter, and every returned id
belongs to the caller in the database. The parameter is ignored.

**6. Nothing in my brief turned out to be wrong.** Both bounded items were real, the invariants were
the right eight to attack, and the co-signed-grants addendum was correct.
