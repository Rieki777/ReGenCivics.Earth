## 4a · How to recover a lane you cannot talk to

**The four in-flight lanes are background agents of the session that dispatched them.** A new session
cannot message them and will not receive their reports. **This is the main thing that breaks across a
handoff, so recover them from disk rather than waiting.**

Every lane was told to **commit at every milestone and push nothing**, so their work is on local
branches in their own worktrees. For each row in §4:

```
cd <worktree> && git log --oneline origin/main..HEAD    # what it finished
cd <worktree> && git status --porcelain                 # what it was still holding
```

**Read the commits before deciding anything.** A lane that committed three times and stopped has
usually done most of the work, and the commit messages in this program carry the reasoning.

Then one of three moves, and the choice is about how much context the work needs rather than how much
is left:

1. **Finish it yourself** if the remaining work is mechanical (gates, a rebase, the report).
2. **Re-dispatch a fresh lane with the same brief**, adding a section naming what the previous one
   already committed so it does not redo it. **The briefs are all in `docs/integration-program/` and
   are self-contained by design**, which is what makes this cheap.
3. **Abandon the branch** if the ruling behind it has moved. Check §8 rulings first: **R90 reversed
   R85 within a day and invalidated code that had already shipped**, so a lane's premise going stale
   is normal here rather than exceptional.

**Do not push a lane branch you have not read.** Nothing in flight has been through CI or a
coordinator review, and the program's standing ladder is CODED, then VERIFIED (CI green on that exact
SHA and merged), then DONE (deploy marker plus a live probe by somebody who did not write it).

## 5 · The defect to make sure landed

**Any signed-in account can give itself a permanent vote in one HTTP request.** Six links, each
correct on its own, verified by hand at `f254d3d`:

1. `POST /api/forms/submit` (`server/index.ts:7261`) reads `type` **straight from the request body
   with no allowlist**, and stamps `entry.userId` from the caller's own token.
2. `hasMembership` (`:3749`) is true when any submission has type `membership-508` and that id.
3. The member stage rule is a membership rule.
4. `computeStage` takes the highest satisfied rule.
5. `ballot.vote` requires the member stage.
6. `buildElectorate` admits everyone for whom `hasCapability("ballot.vote")` answers true.

**Nothing was exploited: no village has launched and no binding ballot has run.** **CLOSED by Lane ROLL,
merged as PR #112 at `29473e4`.** Two things it found that matter more than the fix: **the Love Letter
page has never sent an authorization header in any commit**, so a genuine signing has always stored a
null user id and never once satisfied the rule the exploit used; and **nothing wrote the membership
flag** except a boot migration that already ran. **So the exploit was the only live path to membership,
and closing it without adding a legitimate path would have sealed the door.** Signing and admission are
now separate acts, with admission gated on a TRANSFERABLE capability so a village can take it.

**One judgement left for the founder:** an honest membership row and a forged one are byte-identical by
construction. It does not matter here, because a legitimate row cannot carry a user id at all. **On any
deployment where somebody did attach a token, assume forged.**
