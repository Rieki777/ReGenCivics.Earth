## 2026-07-16 (later): Foundation audit carryover, CI builds a real database from scratch

- **The audit's Carryover A diagnosis was wrong, and measuring it changed the fix** (`fb1d47b`, ADR-37). The audit held that `run-migration.ts` applies "only `0048+`" and that the base schema was trapped in the frozen drizzle-kit journal. The runner has always discovered every file from `0000` (it filters on `/^\d{4}.*\.sql$/`), and `0000`-`0047` are all recorded in `_migrations_applied`; the audit most likely read "one file pending on the dev DB" as "only applies 0048+". Replaying all 194 files onto a genuinely empty MySQL 9.4 gives **157 applied, 36 failed** across five unrelated causes. The keystone: `0096_game_system.sql` quotes `maxValue` bare, `MAXVALUE` is a MySQL reserved word, so that file is a syntax error, has **never once run**, and cascades into 20 more failures. The table exists in production only because drizzle-kit originally created it with backticks. Also MariaDB-only `IF NOT EXISTS` (`0074`, `0098`), `DROP PROCEDURE` rejected by the prepared-statement protocol (`0037`, `0041`), duplicate `CREATE TABLE` (`0036`, `0040`), and data-dependent seeds (`0105`, `0107`).
- **So the blocker was never the journal, it was 36 broken files.** Rye picked the baseline option before that evidence landed; the evidence strengthens it, since `drizzle-kit push` would also have papered over the broken history. Those files are already applied in production and must never re-run there, so they stay frozen and the result is snapshotted instead: `drizzle/ci-baseline.sql` (generated, structure + a tiny `forumCategories` reference allowlist + the `_migrations_applied` history it covers), loaded by `load-ci-baseline.ts`, then `run-migration.ts --all` on top so **new migrations are still applied and still tested, not skipped**. drizzle-kit stays out entirely, so the frozen-journal rule needs no carve-out. Service container is `mysql:9.4`, matching production, not the `mysql:8` the old block sketched.
